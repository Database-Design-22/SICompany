# 시연 대본 (12/7 최종 발표)

`docker/init` 데이터를 처음 적재한 상태 기준이다. 시연 데이터의 자세한 값은 `docs/demo_data.md`, 각 화면이 실행하는 SQL 전문은 `docs/scenario_sql.md`를 본다.

## 한눈에 보기

| 순서 | 내용 | 시간 |
| --- | --- | --- |
| 슬라이드 1 | 시스템 아키텍처 | 1분 |
| **시연 A** | 인력 배치: 고객이 교체를 요청한다 (기본 + 고도화 ②) | 4분 |
| **시연 B** | 평가: 프로젝트가 끝나고 평가가 공정하게 반영된다 (기본 + 고도화 ①④) | 6분 |
| 슬라이드 2~4 | 성능 향상 기법과 실험 결과 (시연 B의 마지막 SQL에서 이어짐) | 3분 |

  - SQL: 화면마다 아래쪽 **"이 화면이 실행한 SQL"** 을 펼쳐서 보여 준다
- 사용자 바꾸기: 화면 오른쪽 위 **현재 사용자** 목록에서 이름을 고른다 (경영관리팀 → 경영진 → 일반직원으로 묶여 있다).

## 시연 전 준비 (발표 10분 전)

1. DB를 처음 상태로 되돌린다. **확정·제출은 되돌릴 수 없으므로 리허설할 때마다 반드시 한다.**
   ```
   cd docker
   docker compose down -v
   docker compose up -d
   ```
2. 앱을 다시 띄운다 (`./gradlew bootRun`) → http://localhost:8080
3. 브라우저 확대 125%, 현재 사용자는 비워 둔다 (홈에 권한별 메뉴가 보인다).
4. 혹시 모를 상황을 대비해 미리 찍어 둔 시연 영상을 준비한다.

## 시연 A: 인력 배치. 고객이 교체를 요청한다 (약 4분)

> 다온전자가 API 게이트웨이 프로젝트(P26-007)에 투입된 조민경을 바꿔 달라고 요청했습니다.
> 경영관리팀이 이 요청을 처리하고, 나중에 같은 고객사 프로젝트에 조민경을 다시 넣으려 할 때 시스템이 경고하는 흐름입니다.

### A-1. 프로젝트 구조 보기 (30초) · 이현규(경영관리팀)
- **현재 사용자 → 이현규** → 왼쪽 메뉴 **프로젝트 관리** → **다온전자 API 게이트웨이 구축 (P26-007)**
- 보여 줄 것: 팀원과 투입 이력 표. 조민경이 PG로 "투입 중"이다.
- 말할 것: "직원과 프로젝트 사이에 **프로젝트참여**(직무)가 있고, 실제 투입 기간은 그 아래 **투입 이력**으로 따로 둡니다. 같은 프로젝트에 다시 들어오면 이력만 하나 늘어납니다."

### A-2. 교체 요청 수용 (1분 30초)
- 왼쪽 메뉴 **교체 요청** → 접수 상태인 **요청 10**(조민경, 두 번째 줄)의 **수용**
- 수용 화면에서 후임으로 **김지원 (17-0004)** 을 고른다. 표시가 "이 프로젝트 참여 기록 있음 (재투입)"이다.
- **SQL 펼치기 → 수용 ①~⑤** 를 보여 준다.
- 말할 것: "수용은 한 트랜잭션입니다. 요청을 '수용'으로 바꾸고, 대상 투입을 '고객 교체 요청(CUST)'으로 닫고, 후임의 참여가 없으면 만들고, 후임 투입을 다음 날부터 열고, 요청에 연결합니다. 중간에 하나라도 실패하면 전부 롤백되고, 이것을 테스트로도 확인했습니다."
- **수용** → 확인 창 **확인**
- 결과: "교체 요청 10번을 오늘 날짜로 수용했습니다 … 후임 17-0004의 투입 이력 ○번을 열었습니다 (기존 프로젝트참여 사용, 재투입)."

### A-3. 제외 등록 (40초)
- 목록 위 노란 안내의 **요청 10번 제외 등록하러 가기** → 사유 "커뮤니케이션 문제로 교체 요청" 입력 → **제외 등록**
- **SQL 펼치기 → "등록할 때 ①: 유효 기간이 겹치는 지정"**
- 말할 것: "같은 고객사와 직원에 기간이 겹치는 지명·제외가 동시에 있으면 안 되므로 먼저 겹치는 지정을 확인합니다. 근거가 된 교체 요청도 함께 연결합니다."

### A-4. 같은 고객사의 다른 프로젝트에 배정 (1분 20초)
- 왼쪽 메뉴 **인력 배정** → 프로젝트 **(주)다온전자 · P26-011 다온전자 클라우드 전환**
- 보여 줄 것: 조민경이 빨간 줄로 **⚠ 제외**, "근거: 교체 요청 10 (2026-11-08, 담당자 임수아)"가 보인다. 지명된 직원이 있으면 맨 위(파란 줄)에 나온다.
- **SQL 펼치기 → "배정 후보 목록"**: 지금 투입 중이 아닌 개발직원에 그 발주처의 유효한 지정과 근거 교체 요청을 LEFT JOIN한 하나의 SELECT
- 조민경 행에서 직무 PG, 시작일(마지막 투입 다음 날로 자동 입력) 그대로 **배정** → 확인 창에 경고와 근거 → **확인**
- 결과: "… ※ 이 발주처의 제외 인력을 확인 후 배정했습니다."
- 말할 것: "제외는 막지 않고 근거와 함께 경고만 합니다. 판단은 사람이 합니다."

### (여유가 있으면) A-5. 철수 사유로 이어짐 (20초)
- **프로젝트 관리 → P26-007**: 조민경 행의 철수사유가 **고객 교체 요청 (CUST)**, 김지원은 재투입 이력이 하나 더 생겼다.

## 시연 B: 평가. 프로젝트가 끝나고 평가가 공정하게 반영된다 (약 6분)

> 평가는 프로젝트가 끝날 때 한 번 합니다. 그래서 몇 달 전 일을 기억하기 어렵고(→ 평가메모),
> PM마다 점수를 후하게 또는 짜게 주는 성향이 다릅니다(→ 점수 보정). 이 두 고도화가 기본 평가 흐름 안에서 어떻게 동작하는지 보여 드립니다.

### B-1. 진행 중에 평가메모 쓰기 (1분) · 김다니엘(PM)
- **현재 사용자 → 김다니엘** → **내 프로젝트** → **가온금융 고객 포털 리뉴얼 (P26-013)** → 류예준 행의 **메모**
- 메모 입력: "11월 설계 리뷰에서 API 명세 누락을 먼저 찾아내 일정 지연을 막음" → **저장**
- **SQL 펼치기 → "메모 대상 (PM이면 팀원 전원, 아니면 투입 기간이 하루 이상 겹친 직원)"**
- 말할 것: "메모는 나중에 평가할 대상에게만 쓸 수 있습니다. PM은 팀원 전원, 동료는 실제로 함께 일한 사람(투입 기간이 하루 이상 겹친 사람)만이고, 작성자 본인만 봅니다."

### B-2. 프로젝트 종료 (1분) · 이현규(경영관리팀)
- **현재 사용자 → 이현규** → **프로젝트 관리** → **P26-013** → **종료** → 확인 창 **확인**
- 결과: "열린 투입 4건을 '계획된 종료'로 닫고, PM평가 3건, 동료평가 9건을 '작성중'으로 만들었습니다." 아래 "이 프로젝트의 평가" 표가 채워진다.
- **SQL 펼치기 → "종료 ③: 평가 대상 쌍"**: PM → 팀원 전원, 동료 → 투입 기간이 겹친 직원을 UNION으로 구한다.
- 말할 것: "종료도 한 트랜잭션입니다. 상태 변경 → 열린 투입 닫기(철수 사유 PLAN) → 평가 행을 슈퍼타입(평가)과 서브타입(PM평가·동료평가)으로 만듭니다. 고객평가는 PM이 고객사에 의뢰할 때 따로 만듭니다."

### B-3. 메모를 보며 평가 제출 (1분 30초) · 김다니엘
- **현재 사용자 → 김다니엘** → **내 평가** → 류예준 · PM · **작성중**의 **작성**
- 보여 줄 것: 오른쪽 "내가 쓴 평가메모"에 B-1에서 쓴 메모가 보인다.
- 점수 9개(0~10)와 업무수행·커뮤니케이션의 장점·단점·바라는 점을 채운다.
- **제출** → 확인 창에 "이 피평가자에 대해 쓴 평가메모 1건이 삭제됩니다" → **제출**
- **SQL 펼치기 → "제출할 때 ① 완성 여부 확인 / ② 상태 '제출' / ③ 평가메모 삭제"**
- 결과: "평가를 제출했습니다. 이 피평가자에 대한 평가메모 1건을 삭제했습니다." 평가는 읽기 전용이 된다.
- 시간이 부족하면: 이 단계 대신 **김직수의 평가 1495**(점수 일부 입력, 메모 36 있음)를 열어 바로 제출해도 같은 동작을 보여 줄 수 있다.

### B-4. 보정 확인과 확정 (2분) · 강현준(경영진)
- **현재 사용자 → 강현준** → **평가 결과·보정**: 2025는 확정, 2026은 **미확정**
- 2026의 **결과 보기** → 위에 "2026년 보정회차는 아직 확정 전" 안내, 방금 제출한 류예준(평가자 김다니엘) 행의 보정점수 칸이 **확정 전**
- 왼쪽 메뉴 **보정 실행** → 2026의 **보정값** → 평가자 성향 표
  - 말할 것: "평가자별로 최근 3년 평균과 같은 유형 전체 평균의 차이를 구해 ±1.5점 안에서 보정값을 정합니다. 평가한 프로젝트가 3개 미만이면 0입니다. +이면 후하게, −이면 짜게 준 평가자입니다."
- **평가 결과·보정** → 2026의 **확정** → 확인 창 **확인** → 다시 **결과 보기**
- 결과: 보정점수가 나타난다 (보정점수 = 원점수 − 적용보정값). 고객평가는 보정하지 않는다.

### B-5. 성능 실험으로 넘어가기 (20초)
- 결과 화면의 **SQL 펼치기 → "평가 결과 (성능 실험 대상)"**
- 말할 것: "이 화면의 평가 결과 조회 SQL이 성능 실험 대상입니다. 평가를 약 10만 건으로 늘려 측정했습니다." → 슬라이드로

## 성능 실험 슬라이드 요약 (`docker/experiment/README.md`)

- 대상: `AdjustmentRepository.FIND_EVAL_RESULTS` (평가 결과 조회, 하나의 SELECT)
- 방법: 제출된 평가 1,254건을 80배 복제해 약 10만 건(점수 75만 행)으로 늘리고 `EXPLAIN ANALYZE`를 3회 실행해 중간값을 쓴다.

| 후보 | 2025 동료 | 2025 PM | 기준 대비 |
| --- | --- | --- | --- |
| 기준 SQL | 416 ms | 251 ms | – |
| A. 인덱스 (EVAL_STAT, EVAL_DT, EVAL_DIV) | 410 ms | 266 ms | 변화 없음 (한 해가 전체의 1/3이라 옵티마이저가 전체 스캔 선택) |
| C. LATERAL 재작성 (구조 변경 없음) | 333 ms | 117 ms | −20% / −53% |
| B. 반정규화 (TB_EVAL.RAW_SCORE) | 223 ms | 92 ms | **−46% / −63%** |

- B와 C의 결과는 기준 SQL과 101,832행 모두 같았다.
- 말할 것: "인덱스는 선택도가 낮아 효과가 없었고, SQL 재작성과 반정규화가 효과가 있었습니다. 반정규화가 가장 빠르지만 점수를 고칠 때마다 원점수를 같이 맞춰야 하는 동기화 책임이 생깁니다."

| 주민등록번호는 어떻게 저장하나요? | 평문을 저장하지 않고 해시로 저장해 가입할 때 해시끼리 대조합니다. 화면에는 어디에도 보여 주지 않습니다. |

## 문제가 생기면

- 버튼을 눌렀는데 이미 처리됐다고 나오면: 리허설 데이터가 남은 것이다. 영상으로 넘어가고, 발표 뒤에 DB를 초기화한다.
- 화면이 안 바뀌면: 브라우저 새로고침. 두 번 제출은 막혀 있다.
